# RFC-010 — E-ticket, QR, dan Wallet

## Metadata dan urutan
- Status: Diusulkan.
- Fitur yang dimiliki: **F34, F35, F36**.
- Kompleksitas: **Tinggi**.
- Prasyarat: **RFC-001, RFC-002, RFC-003, RFC-004, RFC-005, RFC-006, RFC-007, RFC-008, dan RFC-009 wajib selesai dan lulus**.
- Pendahulu langsung: **RFC-009 — Payment dan Refund Sandbox**.
- Penerus langsung: **RFC-011 — Scanner dan Check-in**.
- RFC-011 hanya boleh dimulai setelah Definition of Done RFC ini lulus.
- RFC ini tidak mengimplementasikan kamera, validasi scanner, transisi Used, check-in, atau attempt log.
## Sasaran dan keputusan
Setiap unit pada order Paid menghasilkan tepat satu Ticket melalui transaksi idempoten. QR memuat token acak 256-bit tanpa PII; database mengindeks SHA-256 dan menyimpan token terenkripsi hanya agar pemilik dapat menampilkan ulang QR. Wallet privat menampilkan status `UNUSED`, `USED`, atau `CANCELLED`, dengan `USED` baru dapat dihasilkan RFC-011.
## Ruang lingkup
- Penerbitan tepat satu Ticket per unit order Paid.
- Integrasi issuance ke transaksi pertama `Order PENDING→PAID` dari RFC-009.
- Reconciliation/backfill idempoten untuk order Paid yang belum lengkap.
- Token QR acak aman, hashing, enkripsi envelope/versioned key, dan rotasi.
- Nomor tiket tampilan dan kode manual acak terpisah untuk fallback RFC-011.
- Wallet/list/detail/QR milik pembeli, mobile-first dan tanpa cache publik.
- Pembatalan Ticket Unused ketika event dibatalkan atau refund sandbox Completed.
## Non-scope
- Scanner kamera, validasi token untuk petugas, atomic `UNUSED→USED`, attempt log, dan input manual (RFC-011).
- Transfer/resale tiket, Apple/Google Wallet pass, PDF attachment, print-at-home, seat assignment.
- Email/notifikasi (RFC-013), dashboard/CSV (RFC-012), QR offline trust.
- Penerbitan dari redirect, payment Pending/Failed/Expired, atau late callback reconciliation.
## Gap kondisi setelah RFC-009
- Order dapat Paid secara tepercaya, tetapi belum ada unit fulfillment.
- Replay webhook aman untuk status, namun belum ada constraint tepat satu tiket per unit.
- Refund fulfillment guard belum mempunyai implementasi Ticket.
- Belum ada token QR, endpoint wallet, kebijakan cache, atau key rotation.
## Invarian dan lifecycle
- Untuk order Paid: jumlah Ticket per `order_item_id` akhirnya sama dengan `order_items.quantity`.
- Pasangan `(order_item_id, unit_sequence)` unik dan unit sequence `1..quantity`.
- Order selain Paid tidak dapat menerbitkan Ticket; order Refunded tidak dapat memiliki Ticket Unused baru.
- Satu Ticket memiliki satu token aktif; token mentah tidak disimpan plaintext atau dikirim ke log/analytics.
- Token QR adalah `ti1_<base64url(randomBytes(32))>`; lookup memakai `SHA-256(token + QR_TOKEN_PEPPER)`.
- Ciphertext memakai AES-256-GCM dengan nonce 96-bit unik dan `ticket.id` sebagai AAD; key version eksplisit.
- Status: `UNUSED→USED` dicadangkan RFC-011; `UNUSED→CANCELLED`; `USED` tidak kembali atau dibatalkan oleh refund biasa.
- Event cancellation membatalkan semua Unused secara batch idempoten; Paid/order historis tetap.
- Exactly-once berarti efek database efektif sekali, bukan jaminan eksekusi proses hanya sekali.
## Diagram komponen tekstual
```text
RFC-009 trusted success transaction
  → TicketIssuer(tx) → generate unit/token → TicketRepository → PostgreSQL
                     └→ audit per batch + analytics after commit
Buyer Wallet RSC → TicketQueryService → owner-safe projection
Ticket Detail → QR Render Service → decrypt token in server memory → qrcode PNG
Refund/Event Cancellation → TicketCancellationService → cancel UNUSED only
RFC-011 future validator → TokenHasher → indexed ticket lookup (tanpa decrypt)
```
## Diagram aliran data tekstual
1. Webhook sah mengunci order dan mengubah inventori sesuai RFC-009.
2. Dalam transaction yang sama, issuer membaca item terurut dan mengisi unit sequence yang belum ada.
3. Untuk tiap unit, server membuat token 32 byte, hash berpepper, ciphertext AES-GCM, ticket number, dan manual code.
4. Unique constraints membuat retry/replay tidak dapat menambah unit yang sama.
5. Order baru commit Paid hanya setelah seluruh Ticket dan audit batch berhasil.
6. Wallet mengambil projection berdasarkan `buyer_user_id`; QR didekripsi sesaat di server dan dirender no-store.
7. Refund/cancel event mengunci Ticket terkait dan mengubah hanya Unused menjadi Cancelled.
8. Analytics menerima ID/count setelah commit, tidak pernah token/hash/ciphertext.
## Perubahan skema database eksak
Migration: `0010_eticket_qr_wallet`.
### Enum
- `ticket_status`: `UNUSED`, `USED`, `CANCELLED`.
- `ticket_cancellation_source`: `EVENT_CANCELLED`, `REFUND_COMPLETED`.
- `ticket_issuance_status`: `STARTED`, `COMPLETED`, `FAILED`.

- `order_id TEXT NOT NULL REFERENCES orders(id) ON DELETE RESTRICT`.

- `used_at TIMESTAMPTZ NULL`; `cancelled_at TIMESTAMPTZ NULL`.
- `cancellation_source ticket_cancellation_source NULL`; `cancellation_reference_id TEXT NULL`.
- `created_at`, `updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP`; `version INTEGER NOT NULL DEFAULT 1`.
- Unique `tickets_ticket_number_key(ticket_number)`.
- Unique `tickets_manual_code_key(manual_code)`.
- Unique `tickets_token_hash_key(token_hash)`.

- Index `tickets_event_status_idx(event_id,status,issued_at,id)`.
- Index `tickets_order_idx(order_id,order_item_id,unit_sequence)`.

### Constraint lintas tabel pada service/transaction
- `tickets.order_id = order_items.order_id`.
- `event_id`, `ticket_type_id`, dan `owner_user_id` diturunkan server dari order/item, bukan request.
- `unit_sequence <= order_items.quantity`.
- Order wajib `PAID` pada issuance normal; pada transaksi pertama Paid, issuer menerima transition context tepercaya.
- Trigger database tidak dipakai untuk crypto atau issuance; repository transaction dan unique constraints menjadi boundary.

## Konfigurasi keamanan
- Env wajib: `QR_TOKEN_PEPPER`, `QR_ENCRYPTION_KEYS`, `QR_ACTIVE_KEY_VERSION`.
- Pepper dan key minimum 32 byte, berbeda satu sama lain dan berbeda per environment.
- `QR_ENCRYPTION_KEYS` adalah secret map version→key; startup gagal jika active version hilang.
- Rotasi: tambah key baru, ubah active version, lazy re-encrypt saat akses/job eksplisit; key lama baru dicabut setelah semua row termigrasi.
- Tidak ada default/hardcoded key; production-demo menolak secret test yang dikenal.

## Kontrak internal
### `TicketIssuer.issueForPaidOrder(tx, orderId, correlationId)`
- Hanya dipanggil dalam transaction sukses payment sebelum commit.
- Return `{issuanceRunId,expectedQuantity,issuedQuantity}`.
- Replay mengembalikan batch Completed dan memverifikasi count; mismatch menjadi blocker `TICKET_ISSUANCE_INVARIANT`.

### `TicketCancellationService.cancelUnusedForEvent/refund(tx, reference)`
- Event cancellation membatalkan Unused; Used dipertahankan untuk histori.
- Refund biasa memeriksa ada/tidak Ticket Used sebelum provider refund disetujui.
- Setelah refund Completed, semua Unused order dibatalkan dalam transaction status lokal.

## Kontrak API
Semua endpoint membutuhkan session ACTIVE, owner check server, `Cache-Control: private,no-store`, dan `Vary: Cookie`.

### `GET /api/tickets`
- Auth buyer; query `status?=UNUSED|USED|CANCELLED`, `cursor?`, `limit=1..50` default 20.
- Respons 200 `{items:[{id,ticketNumber,status,event:{slug,title,startsAt,timezone,venueName,city},ticketType:{name},issuedAt}],nextCursor}`.
- Keyset `issued_at,id`; hanya `owner_user_id=session.user.id`.

### `GET /api/tickets/{id}`
- Auth owner; bukan owner/tidak ada sama-sama 404.
- Respons 200 `{ticket:{id,ticketNumber,manualCode,status,issuedAt,event:{slug,title,startsAt,endsAt,timezone,venueName,addressLine,city,province},ticketType:{name},order:{orderNumber},owner:{name},usedAt?,cancelledAt?}}`.
- Nama owner berasal akun sendiri; email/username tidak diperlukan.

### `GET /api/tickets/{id}/qr`
- Auth owner; hanya Ticket `UNUSED`; rate 30/user/menit.
- Respons 200 `image/png`, content disposition inline, `Cache-Control: private,no-store,max-age=0`, `X-Content-Type-Options: nosniff`.
- Ukuran default 320×320, error correction `M`, quiet zone 4; query ukuran tidak diterima.
- Cancelled/Used mengembalikan `409 TICKET_QR_UNAVAILABLE`; body error JSON, bukan gambar.

### `POST /api/internal/jobs/reconcile-ticket-issuance`
- Auth signed scheduler/operator; body `{batchSize:1..100}`.
- Memilih order Paid dengan count kurang, lock `SKIP LOCKED`, lalu issuer idempoten.
- Respons `{scanned,repaired,failed,hasMore}` tanpa token/PII.

## State dan caching
- Database menjadi source of truth; wallet initial fetch melalui RSC.
- Filter/status/cursor berada di URL; local state hanya dialog dan loading QR.
- Tidak ada public cache, service worker cache, prefetch QR, atau localStorage token.
- Blob QR direvoke saat komponen unmount/visibility berubah; screenshot pengguna berada di luar kontrol, diberi peringatan.
- Setelah cancel/issuance, invalidasi private route cache dan UI melakukan refresh server.

## Algoritma/pseudocode
```text
issueForPaidOrder(tx, order):
  require trusted payment transition or persisted order PAID
  items = lock/read order items ORDER BY id
  expected = sum(quantity); claim issuance run unique(order)
  for item in items:
    for sequence in 1..item.quantity:
      if unique unit exists: continue
      raw = "ti1_" + base64url(randomBytes(32))
      hash = sha256(raw + pepper)
      encrypted = aes256gcm(activeKey, randomNonce12, raw, aad=ticketId)
      insert ticket with derived owner/event/type, random display identifiers
  require count tickets(order)=expected
  complete run; append one audit summary

renderQr(actor,ticketId):
  fetch owner ticket projection; require UNUSED
  decrypt ciphertext by keyVersion using ticketId AAD
  verify sha256(raw+pepper)==tokenHash
  render PNG in memory; zero/release buffers where runtime allows; return no-store
```

## UI/UX
- `/tickets` memprioritaskan tiket event terdekat, kartu besar mobile, filter status, dan empty state.
- Detail menampilkan judul, jadwal/zona, venue, jenis, ticket number, pemilik order, dan badge status.
- Tombol “Tampilkan QR” memuat on-demand; QR tidak dirender di list/prefetch.
- QR memiliki brightness tinggi, quiet zone, instruksi perbesar, dan peringatan jangan membagikan.
- Used/Cancelled tidak menampilkan QR; alasan status dan langkah kembali ke wallet jelas.
- Manual code tampil dengan grouping empat karakter dan tombol copy untuk fallback petugas RFC-011.

## Error, log, dan monitoring
- Kode: `TICKET_NOT_FOUND`, `TICKET_NOT_ISSUED`, `TICKET_ISSUANCE_INVARIANT`, `TICKET_TOKEN_COLLISION`, `TICKET_CRYPTO_FAILED`, `TICKET_QR_UNAVAILABLE`, `TICKET_CANCELLED`, `TICKET_ACCESS_DENIED`.
- Collision token/manual code/ticket number di-retry maksimal lima; sesudah itu transaction gagal.
- Log: order/ticket/issuance IDs, count, key version, outcome, duration, correlation; tanpa raw token, hash, ciphertext, manual code, owner PII.
- Audit: `ticket.issued_batch`, `ticket.cancelled_batch`, `ticket.key_rotated`; analytics `ticket_issued`, `ticket_viewed`.
- Metrik: issuance count/mismatch/retry, QR render p95/error, wallet p95, key version distribution, reconciliation backlog; invariant mismatch alert segera.

## Keamanan dan privasi
- Token 256-bit CSPRNG, PII-free, berpepper, terenkripsi at rest, dan hanya didekripsi server untuk owner.
- QR adalah bearer identifier tetapi keputusan validasi tetap server RFC-011; tidak menandatangani status di payload.
- Owner check dilakukan sebelum decrypt; error bukan owner disamakan 404.
- CSP halaman melarang third-party image/script tak perlu; QR tidak masuk telemetry, URL, referer, atau analytics.
- Manual code memiliki 80-bit entropy; RFC-011 wajib rate limit dan tidak membocorkan valid/tidak sebelum authorization event.

## Kinerja, aksesibilitas, dan i18n
- Issuance maksimum 50 unit/order secara defensif meski batas saat ini 5 per tipe; bulk insert dalam transaction.
- Wallet projection eksplisit dan keyset; QR dibuat on-demand ≤200 KB, target render p95 ≤500 ms.
- Status teks+ikon, heading/focus benar, alt “Kode QR tiket …”, kontras dan keyboard WCAG 2.1 AA.
- QR diberi deskripsi non-visual/manual code; layout 320 px tanpa overflow dan target Chrome/Edge/Firefox/Safari terbaru.
- Copy Bahasa Indonesia, Rupiah tidak diperlukan di QR, waktu mengikuti timezone event.

## Dependensi dan fallback
- Memakai Paid/webhook/refund RFC-009, order/item RFC-008, event RFC-005–007, auth/audit RFC-002/003.
- Library `qrcode` versi yang disetujui RULES; crypto memakai Node.js built-in, tanpa library crypto baru.
- Jika renderer gagal, tampilkan retry dan manual code; jangan mengekspos raw token sebagai teks.
- Jika key version hilang/decrypt gagal, fail closed, alert, QR tidak diberikan; tidak membuat token baru diam-diam.
- Analytics gagal tidak rollback; audit/crypto/database gagal membuat payment transition rollback pada issuance sinkron.

## Kasus uji
- `F34-INT-001`: quantity N menghasilkan N unit unik; Pending/Failed/Expired/late tidak menghasilkan tiket.
- `F34-CONC-002`: dua replay/reconciliation paralel menghasilkan satu Ticket per unit.
- `F34-INT-003`: kegagalan unit tengah rollback payment Paid, counter conversion, seluruh Ticket, dan audit.
- `F35-SEC-001`: entropy/format, hash lookup, AES-GCM tamper, wrong AAD/key version fail closed.
- `F35-SEC-002`: token/PII tidak ada di log, URL, analytics, HTML awal, atau response non-owner.
- `F36-INT-001`: owner-only list/detail/QR; status filter/cursor stabil.
- `F36-E2E-002`: mobile wallet→detail→QR; Used/Cancelled QR ditolak.
- Refund/event cancel: Unused cancelled, Used guard, replay satu efek.
- Rotation test: old/new key dapat decrypt selama migrasi dan old key aman dicabut setelah nol row.

## Migrasi dan rollout
1. Regression RFC-001–009, backup preview, env crypto per environment, dan secret scan lulus.
2. Tambah enum/tabel/index; deploy crypto self-test dan repository tanpa route publik.
3. Integrasikan issuer ke transaction payment di balik flag; uji rollback dan replay sandbox.
4. Jalankan backfill idempoten untuk order Paid preview, verifikasi count dengan query invariant.
5. Buka wallet/detail lalu QR; monitor key version, render error, dan access denied.
6. Rollback menutup route/issuer baru; Ticket historis tidak dihapus dan key lama dipertahankan.

## Risiko dan mitigasi
- Tiket ganda dari replay: unique unit + transaction + reconciliation idempoten.
- Payment Paid tanpa tiket: issuance satu transaction dan invariant/backlog alert.
- Token bocor: owner-only on-demand, no-store, no logs, PII-free, CSP.
- Key hilang/rotasi gagal: versioning, backup secret manager, preflight, staged re-encryption.
- QR screenshot dibagikan: bearer token tetap hanya dapat dipakai sekali setelah RFC-011; edukasi pengguna.
- Refund vs issuance race: lock order dan refund fulfillment guard dalam transaction.

## Kriteria penerimaan per fitur
- **F34:** setiap unit order Paid menghasilkan tepat satu Ticket; status lain/replay tidak menambah Ticket; kegagalan rollback atomik.
- **F35:** tiap Ticket mempunyai token 256-bit unik tanpa PII, hash unik, enkripsi versioned, dan validasi final tetap server.
- **F36:** hanya pemilik melihat wallet/detail/QR, data event/tipe/pemilik/status lengkap, dan status berubah konsisten setelah cancel/refund.

## Definition of Done
1. Seluruh RFC-001–009 dan regression suite lulus.
2. Migration/constraints/index, crypto config, key rotation, backup, dan rollback diuji preview.
3. Exactly-one issuance dibuktikan untuk replay, konkurensi, partial failure, dan reconciliation PostgreSQL.
4. Refund/event cancellation mengimplementasikan guard: Unused batal, Used ditolak/dipertahankan sesuai aturan.
5. Unit/integration/security/E2E/performance F34–F36 lulus; module branch coverage ≥90%.
6. Wallet/QR mobile, Indonesia, private no-store, empat browser target, dan WCAG 2.1 AA terverifikasi.
7. Tidak ada token/PII di log/analytics/cache; secret scan dan crypto tamper test lulus.
8. Format/lint/typecheck/build/test/security scan lulus tanpa blocker, Critical/High, TODO, atau fallback secret.
9. Tidak ada scanner, camera access, validation endpoint petugas, transisi Used, check-in, attempt log, atau forward implementation RFC-011+.
10. RFC-011 baru dimulai setelah exit criteria ini disetujui.
