# RFC-008 — Order, Inventori, Reservasi, dan Expiry

## Metadata dan urutan
- Status: Diusulkan.
- Fitur yang dimiliki: **F16, F23, F24, F25, F26, F27, F28, F59, F65**, serta **F75 Must Have bagian akun, ledger/reservasi, dan redemption checkout**; penyelesaian earn/debit/reversal/restoration F75 dimiliki RFC-009.
- Kompleksitas: **Sangat tinggi**.
- Prasyarat: **RFC-001, RFC-002, RFC-003, RFC-004, RFC-005, RFC-006, dan RFC-007 wajib selesai dan lulus**.
- Pendahulu langsung: **RFC-007 — Katalog dan Discovery**.
- Penerus langsung: **RFC-009 — Payment dan Refund Sandbox**.
- RFC-009 hanya boleh dimulai setelah Definition of Done RFC ini lulus.
- Implementasi wajib sekuensial; RFC ini tidak membuat payment, webhook, refund, tiket, QR, atau check-in.
## Sasaran dan keputusan
Pembeli terautentikasi dapat membuat satu order untuk satu event dengan snapshot harga server-side dan reservasi tepat 15 menit tanpa overselling. Mode inventori menentukan apakah yang ditahan adalah kuota kategori atau kursi spesifik. Counter inventori, hold kursi, order, item, reservasi, dan idempotency record dibuat atomik di PostgreSQL. Waktu database menjadi otoritas. Retry checkout efektif tepat sekali untuk key dan payload yang sama. F65 diselesaikan pada RFC ini.
## Ruang lingkup
- Pemilihan beberapa tipe tiket dari satu event, masing-masing 1–5 unit, atau pemilihan kursi bernomor pada `RESERVED_SEATING`.
- Batas kumulatif lima unit per akun, event, dan tipe untuk Paid plus reservasi aktif.
- Ringkasan checkout server-side dan konfirmasi eksplisit, termasuk label kategori/kursi.
- Lifecycle order `PENDING`, `PAID`, `FAILED`, `EXPIRED`, `CANCELLED`, `REFUNDED`; RFC ini hanya menghasilkan `PENDING`, `EXPIRED`, dan pembatalan internal sebelum payment.
- Counter `reserved_quantity` dan `paid_quantity` sebagai sumber ketersediaan konsisten pada GA/Zoned.
- Hold kursi 15 menit: satu `EventSeat` paling banyak satu hold aktif; error `SEAT_UNAVAILABLE` dan `INVENTORY_MODE_MISMATCH`.
- Reservasi 15 menit, expiry idempoten, scheduler multi-worker, dan status order pembeli.
- Idempotency key checkout berscope pengguna selama 24 jam.
- Loyalty pembeli-organizer F75: 1 poin = Rp10, redemption maksimum 20% subtotal, tidak kedaluwarsa, terisolasi pada organizer yang sama, dan tidak bernilai tunai.
## Non-scope
- Membuat transaksi provider, instruksi payment, webhook, refund, atau mengubah order menjadi Paid (RFC-009).
- Menerbitkan tiket/QR (RFC-010) dan check-in (RFC-011).
- Cart lintas event, voucher, fee, pajak, waiting list, dynamic pricing, guest checkout.
- Clickable map, editor drag-and-drop, orphan-seat optimization, atau collaborative editing.
- Pemberian poin dari Paid, konversi reservation menjadi debit, dan reversal/restoration refund (RFC-009).
- Mengubah harga/kuota authoring; RFC ini hanya membaca konfigurasi RFC-005/006.
- Memilih provider scheduler; decision gate harus ditutup, adapter pemicu tetap tipis.
## Gap kondisi setelah RFC-007
- Detail event hanya menampilkan sale eligibility; tidak ada stok aktual atau checkout.
- `event_ticket_types.quota` belum memiliki counter reserved/Paid.
- Belum ada order, item snapshot, reservasi, idempotency store, atau expiry worker.
- Cache katalog dapat stale dan tidak dapat menjadi dasar keputusan kuota.
## Invarian dan transisi
- `0 <= reserved_quantity`, `0 <= paid_quantity`, dan `reserved_quantity + paid_quantity <= quota`.
- Ketersediaan kategori adalah `quota - reserved_quantity - paid_quantity`, dihitung dari row terkunci.
- Pada `RESERVED_SEATING`, satu `event_seat_id` paling banyak satu hold aktif (`released_at IS NULL`) atau satu Ticket Paid.
- Payload checkout yang tidak sesuai `inventory_mode` ditolak `INVENTORY_MODE_MISMATCH`; kursi di-hold/Paid ditolak `SEAT_UNAVAILABLE`.
- Mode inventori tidak boleh diubah setelah order atau reservasi ada.
- Semua item dalam order wajib berasal dari satu event Published, belum dimulai, tidak dihentikan, dan berada pada window jual.
- `expires_at` selalu `created_at + INTERVAL '15 minutes'` berdasarkan `transaction_timestamp()`.
- Pada `now >= expires_at`, order tidak lagi dapat dibayar; tepat pada batas waktu dianggap kedaluwarsa.
- Reservasi aktif adalah `released_at IS NULL`; pelepasan mengurangi counter tepat sekali.
- Transisi RFC ini: `PENDING→EXPIRED` dan `PENDING→CANCELLED`; status terminal tidak dapat kembali.
- Protokol lintas RFC: lock order dahulu bila sudah ada, lalu loyalty account, lalu seluruh tipe tiket menurut `id ASC`, lalu `EventSeat` terurut bila reserved seating; RFC-009 wajib mengikuti urutan ini.
- Key sama+payload sama mengembalikan order sama; key sama+payload berbeda selalu `409`.

## Diagram aliran data tekstual
1. Client mengirim tipe/jumlah atau `seatIds`, dan `Idempotency-Key`, tanpa harga.
2. Boundary memvalidasi session, CSRF, body, key, rate limit, lalu menghitung canonical request hash.
3. Transaction mengklaim idempotency record, mengunci semua tipe tiket terurut, dan mengunci kursi terurut bila mode reserved.
4. Service memvalidasi event, mode, window, batas akun, dan ketersediaan dari database.
5. Order, snapshot item/kategori/kursi, reservasi atau hold, dan kenaikan counter dibuat dalam transaction yang sama.
6. Audit atomik ditulis; commit menghasilkan order `PENDING` dan expiry tepat 15 menit.
7. Scheduler memilih order due dengan `FOR UPDATE SKIP LOCKED`, melepas setiap reservasi aktif, lalu menandai `EXPIRED`.
8. UI selalu membaca ulang status server; timeout client tidak mengubah state lokal secara optimistik.

## Kontrak API
Semua response privat `Cache-Control: private,no-store`; Zod, correlation ID, envelope error, dan server authorization wajib.
### `POST /api/checkout/summary`
- Auth: user ACTIVE; CSRF; rate 30/user/menit.
- Request: `{"eventId":"...","items":[{"ticketTypeId":"...","quantity":2}]}`; 1–10 tipe unik.
- Request menerima `redeemPoints?` integer `>=0`.
- Respons 200: `{event,items:[{ticketTypeId,name,quantity,unitPriceRupiah,lineTotalRupiah,availability}],subtotalRupiah,requestedRedeemPoints,appliedRedeemPoints,loyaltyDiscountRupiah,totalPayableRupiah,currency:"IDR",reservationMinutes:15}`.
- Tidak membuat data; hasil dapat berubah saat konfirmasi.
### `POST /api/orders`
- Auth: user ACTIVE; CSRF; rate 10/user/menit.
- Header wajib `Idempotency-Key`: 16–128 karakter ASCII opaque; server menyimpan SHA-256.
- Request sama dengan summary ditambah `confirmed:true`.
- Respons 201 pertama/200 replay: `{order:{id,orderNumber,status:"PENDING",items,subtotalRupiah,redeemedPoints,loyaltyDiscountRupiah,totalPayableRupiah,currency:"IDR",expiresAt,serverTime}}`.
- `409 IDEMPOTENCY_KEY_REUSED` jika canonical payload hash berbeda; processing lama mengembalikan `409 IDEMPOTENCY_IN_PROGRESS` + `Retry-After: 1`.
### `GET /api/orders/{id}`
- Auth owner atau ADMIN; owner hanya projection miliknya.
- Respons 200: `{order:{id,orderNumber,event,items,subtotalRupiah,redeemedPoints,loyaltyDiscountRupiah,totalPayableRupiah,currency,status,expiresAt,serverTime}}`.
- `404` generik untuk bukan owner; ADMIN access dicatat.
### `GET /api/orders?cursor&limit`
- Auth user ACTIVE; hanya order sendiri; limit 1–50 default 20.
- Respons 200 `{items:[...safeSummary],nextCursor}` dengan keyset `created_at,id`.
### `POST /api/internal/jobs/expire-orders`
- Auth: secret scheduler terpisah atau signed platform invocation; bukan session user.
- Request opsional `{"batchSize":100}`; maksimum 500.
- Respons 200 `{scanned,expired,releasedReservations,hasMore,durationMs}`.
- Invocation ID wajib untuk log; endpoint tidak mengembalikan data pembeli.
## State dan caching
- Database adalah source of truth order/inventori; tidak ada optimistic mutation.
- Countdown memakai `expiresAt-serverTime`, hanya informasional; server tetap memutuskan expiry.
- React state lokal hanya pilihan sebelum submit dan dialog konfirmasi.
- Detail publik boleh menampilkan kategori `AVAILABLE|LOW|SOLD_OUT`, tetapi endpoint checkout tidak pernah percaya cache.
- Setelah reserve/release, invalidasi tag `event:{id}` dan `events:list` best effort; kegagalan cache tidak rollback transaksi.
- Idempotency response disimpan tersanitasi; key mentah tidak disimpan atau dicatat.

## Algoritma/pseudocode
```text
createOrder(actor, key, input):
  canonical = sort unique items by ticketTypeId; requestHash = sha256(canonical)
  transaction SERIALIZABLE:
    claim actor/scope/sha256(key); replay or reject mismatch
    lock event; if redeemPoints>0 lock buyer+event-organizer loyalty account
    lock ticket types ORDER BY id
    dbNow = transaction_timestamp()
    validate Published, windows, same event, not stopped, before event
    for each type:
      existing = Paid + active reservation quantity for actor/event/type
      require existing + requested <= 5
      require quota - paid_quantity - reserved_quantity >= requested
    create order(createdAt=dbNow, expiresAt=dbNow+15m), items, reservations
    increment each reserved_quantity with guarded UPDATE
    append audit; complete idempotency response
  retry serialization/deadlock max 3 with jitter; return

expireBatch():
  transaction:
    select due PENDING orders where expires_at <= statement_timestamp()
      order by expires_at,id for update skip locked limit N
    for each order:
      lock referenced loyalty account if any
      lock ticket types by id
      for active reservations: decrement reserved_quantity; mark released EXPIRED
      release ACTIVE loyalty reservation and decrement reserved_points once
      conditional update order PENDING→EXPIRED; append one audit
```

## Keamanan, performa, aksesibilitas, dan i18n
- Semua harga/status/ownership dihitung server; CSRF, rate limit, object authorization, dan parameterized SQL wajib.
- CUID tidak menggantikan authorization; response user lain tetap 404.
- 50 checkout bersamaan untuk satu tipe diuji 15 menit; overselling nol dan create order p95 target internal ≤2 detik.
- Lock terurut, batch `SKIP LOCKED`, projection eksplisit, tanpa `COUNT(*)` pada list.
- Form semantic, label jumlah, ringkasan error, focus management, status tidak hanya warna, target WCAG 2.1 AA.
- Layout 320 px tanpa overflow; Bahasa Indonesia, integer Rupiah, timestamp UTC ditampilkan pada timezone event.
## Dependensi dan fallback
- Memakai event/ticket type RFC-005/006, katalog RFC-007, auth RFC-002, audit/analytics RFC-003, dan fondasi RFC-001.
- Scheduler harus dipilih sebelum rollout; jika invocation eksternal gagal, operator dapat menjalankan command idempoten terautentikasi.
- Tidak ada expiry via timer browser. Jika cache gagal, baca database. Jika analytics gagal, transaksi tetap commit; audit/database gagal rollback.
- Jika provider scheduler belum dipilih, RFC tidak dapat dinyatakan selesai; tidak boleh membuat interval in-process pada runtime serverless.
## Kasus uji
- `F16-CONC-001`: 50 request pada sisa satu, tepat satu reservasi berhasil dan counter valid.
- `F65-CONC-001`: dua pembeli memilih kursi yang sama; tepat satu hold aktif dan yang lain `SEAT_UNAVAILABLE`.
- `F65-INT-002`: payload GA dengan `seatIds` atau reserved tanpa kursi menghasilkan `INVENTORY_MODE_MISMATCH`.
- `F65-TIME-003`: hold 15 menit dilepas sekali pada expiry; kursi tersedia kembali.
- `F23-INT-001`: tipe lintas event, jumlah nol/>5, window/stop-sale ditolak.
- `F23-INT-002`: batas kumulatif Paid+aktif per akun/event/type maksimal lima.
- `F24-INT-001`: harga dan total selalu dari database; perubahan sebelum confirm terdeteksi.
- `F25-INT-001`: snapshot, owner projection, order number, dan transisi invalid.
- `F26-TIME-001`: sebelum batas aktif; tepat `expires_at` expired; release sekali.
- `F27-CONC-001`: rollback request multi-item gagal tidak meninggalkan item/reservasi/counter parsial.
- `F28-INT-001`: same key/same payload replay; payload beda 409; timeout retry satu order.
- `F59-CONC-001`: dua worker dan replay job menghasilkan satu expiry/audit/release.
- `F59-RACE-002`: contract race expiry/payment memakai lock order dahulu dan boundary waktu konsisten.
- `F16-PERF-001`: 50 pembeli/5.000 kuota/15 menit, nol oversell dan latensi tercatat.
- E2E: detail→summary→confirm→countdown→expiry→stok kembali.
## Migrasi dan rollout
1. Pastikan regression RFC-001–007 lulus, decision gate scheduler ditutup, dan backup preview tersedia.
2. Tambah enum/tabel/counter default nol; validasi seluruh quota lama memenuhi constraint.
3. Deploy read availability, lalu summary, create order, dan status di balik feature flag.
4. Aktifkan scheduler pada preview, uji clock boundary, multi-worker, retry, dan expiry lag.
5. Load test konkurensi sebelum membuka checkout demo; monitor counter dan audit.
6. Rollback menutup checkout/scheduler; data order tidak dihapus, migration contract ditunda sampai aman.
## Risiko dan mitigasi
- Overselling/lost update: row lock terurut, guarded update, constraint, dan concurrent PostgreSQL test.
- Double-sell kursi: partial unique hold aktif, lock `EventSeat`, dan `F65-CONC-001`.
- Deadlock multi-item: sort ID dan retry terbatas.
- Clock client salah: waktu database + `serverTime`.
- Job terlambat: stok tetap dianggap aktif sampai transaksi release; alert expiry lag dan job manual idempoten.
- Key abuse/storage growth: hash, scope per actor, rate limit, expiry 24 jam, cleanup terjadwal.
- Cache stale: hanya label; checkout memvalidasi database.
- Race payment mendatang: protokol lock dan batas `now < expires_at` wajib RFC-009.
## Kriteria penerimaan per fitur
- **F16:** ketersediaan konsisten `quota-paid-reserved`, tidak negatif, dan checkout bersamaan tidak melampaui kuota.
- **F23:** pembeli memilih tipe satu event dan jumlah positif dengan batas kumulatif lima per akun/event/type.
- **F24:** ringkasan dan total dihitung ulang server, dikonfirmasi, serta perubahan ditampilkan jelas.
- **F25:** order unik menyimpan owner/snapshot/status dan hanya transisi serta akses yang sah diterima.
- **F26:** order dan reservasi dibuat atomik selama tepat 15 menit lalu dilepas sekali.
- **F27:** sisa satu hanya memberi satu keberhasilan dan kegagalan multi-item tidak parsial.
- **F28:** retry key+payload sama mengembalikan order sama; key reuse berbeda ditolak.
- **F59:** scheduler idempoten, multi-worker-safe, tidak meng-expire non-Pending, dapat dipantau dan diulang.
- **F65:** selector list/grid aksesibel, denah statis hanya penjelasan, hold 15 menit, satu kursi satu hold, snapshot kategori/label, serta error mode-aware.
- **F75 (RFC-008):** akun loyalty unik per pembeli-organizer menyediakan balance/ledger append-only; checkout organizer yang sama dapat mereservasi poin tanpa expiry dengan rasio Rp10/poin dan batas diskon 20%, menyimpan subtotal/diskon/total payable, serta melepas reservasi tepat sekali pada expiry/failure/cancel.

## Ekstensi F75 — Akun, Ledger, Reservasi, dan Redemption Loyalty

Bagian ini adalah kontrak otoritatif F75 untuk RFC-008. Istilah `total_rupiah` pada kontrak lama digantikan oleh snapshot `subtotal_rupiah`, `loyalty_discount_rupiah`, dan `total_payable_rupiah`; RFC-009 wajib menagih tepat `total_payable_rupiah`.

### Aturan domain
- Satu akun loyalty dimiliki tepat satu pasangan `(buyer_user_id, organizer_profile_id)`. Poin yang diperoleh dari organizer A tidak dapat dibaca, direservasi, atau ditukar pada event organizer B.
- Poin tidak memiliki expiry, tier, transfer, pooling, gift, purchase, atau cash-out. Pada seluruh UI poin berlabel manfaat loyalty sandbox tanpa nilai tunai.
- Rasio tetap F75 adalah `1 point = Rp10`. `subtotalRupiah = sum(lineTotalRupiah)` dan wajib `<= MAX_ORDER_SUBTOTAL_RUPIAH` sebesar Rp9.000.000.000.000. `maxDiscountRupiah = floor(subtotalRupiah / 5)`. `maxRedeemablePoints = floor(maxDiscountRupiah / 10)`.
- `appliedRedeemPoints = min(requestedRedeemPoints, maxRedeemablePoints, availablePoints)`, tetapi request yang melebihi available ditolak `LOYALTY_INSUFFICIENT_POINTS`; request yang melebihi cap 20% ditolak `LOYALTY_REDEMPTION_LIMIT_EXCEEDED` agar client tidak dapat mengubah intent diam-diam.
- `loyaltyDiscountRupiah = appliedRedeemPoints * 10`; `totalPayableRupiah = subtotalRupiah - loyaltyDiscountRupiah`. Seluruh operasi memakai integer/BIGINT tanpa float.
- `net_points = balance_points - debt_points`; `available_points = max(balance_points - reserved_points - debt_points,0)`. `debt_points` hanya bertambah pada reversal RFC-009; earn/restore berikutnya menaikkan balance sehingga secara efektif melunasi debt sebelum tersedia untuk redemption.
- Checkout hanya mereservasi poin; balance belum didebit sampai Paid tepercaya RFC-009. Reservation ACTIVE dilepas tepat sekali jika order Expired, Failed, Cancelled, event Cancelled, create payment gagal terminal, atau payment gagal/expired.

### Skema database eksak
Migration tetap `0008_order_inventory_reservation` dan menambah objek berikut.

Enum:
- `loyalty_entry_type`: `EARN`, `REDEEM_DEBIT`, `EARN_REVERSAL`, `REDEEM_RESTORE`.
- `loyalty_reservation_status`: `ACTIVE`, `CONSUMED`, `RELEASED`.
- `loyalty_release_reason`: `ORDER_EXPIRED`, `ORDER_FAILED`, `ORDER_CANCELLED`, `EVENT_CANCELLED`, `PAYMENT_FAILED`, `PAYMENT_EXPIRED`.

Tabel `loyalty_accounts`:
- `id TEXT PRIMARY KEY` (CUID).
- `buyer_user_id TEXT NOT NULL REFERENCES users(id) ON DELETE RESTRICT`.
- `organizer_profile_id TEXT NOT NULL REFERENCES organizer_profiles(id) ON DELETE RESTRICT`.
- `balance_points BIGINT NOT NULL DEFAULT 0`; `debt_points BIGINT NOT NULL DEFAULT 0`; `reserved_points BIGINT NOT NULL DEFAULT 0`.
- `created_at`, `updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP`; `version INTEGER NOT NULL DEFAULT 1`.
- Unique `loyalty_accounts_buyer_organizer_key(buyer_user_id,organizer_profile_id)`.
- Checks `balance_points>=0`, `debt_points>=0`, `reserved_points>=0`, `reserved_points<=balance_points`, dan `version>0`.
- Index `loyalty_accounts_organizer_buyer_idx(organizer_profile_id,buyer_user_id)`.

Tabel append-only `loyalty_ledger_entries`:
- `id TEXT PRIMARY KEY` (CUID); `account_id TEXT NOT NULL REFERENCES loyalty_accounts(id) ON DELETE RESTRICT`.
- `entry_type loyalty_entry_type NOT NULL`; `points_delta BIGINT NOT NULL`; `source_key VARCHAR(191) NOT NULL`.
- `order_id TEXT NOT NULL REFERENCES orders(id) ON DELETE RESTRICT`; `refund_id TEXT NULL` (foreign key ke `refunds(id)` ditambahkan additive oleh migration RFC-009 setelah tabel tersedia).
- `balance_points_after BIGINT NOT NULL`; `debt_points_after BIGINT NOT NULL`; `occurred_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP`.
- `actor_type VARCHAR(20) NOT NULL CHECK (actor_type IN ('SYSTEM','ADMIN'))`; `correlation_id VARCHAR(80) NOT NULL`.
- Unique `loyalty_ledger_account_source_type_key(account_id,source_key,entry_type)`.
- Checks: delta `>0` untuk `EARN|REDEEM_RESTORE`, delta `<0` untuk `REDEEM_DEBIT|EARN_REVERSAL`; after values nonnegative; `refund_id IS NULL` untuk `EARN|REDEEM_DEBIT`.
- Index `loyalty_ledger_account_time_idx(account_id,occurred_at DESC,id DESC)` dan `loyalty_ledger_order_idx(order_id,entry_type)`.
- Trigger database `loyalty_ledger_entries_append_only` menolak `UPDATE` dan `DELETE` untuk role aplikasi; koreksi hanya entry kompensasi baru.

Tabel `loyalty_point_reservations`:
- `id TEXT PRIMARY KEY` (CUID); `account_id TEXT NOT NULL REFERENCES loyalty_accounts(id) ON DELETE RESTRICT`.
- `order_id TEXT NOT NULL REFERENCES orders(id) ON DELETE RESTRICT`.
- `points BIGINT NOT NULL`; `discount_rupiah BIGINT NOT NULL`; `status loyalty_reservation_status NOT NULL DEFAULT 'ACTIVE'`.
- `release_reason loyalty_release_reason NULL`; `reserved_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP`.
- `consumed_at TIMESTAMPTZ NULL`; `released_at TIMESTAMPTZ NULL`; `updated_at TIMESTAMPTZ NOT NULL DEFAULT CURRENT_TIMESTAMP`; `version INTEGER NOT NULL DEFAULT 1`.
- Unique `loyalty_point_reservations_order_key(order_id)`.
- Checks: `points BETWEEN 1 AND 180000000000`, `discount_rupiah=points*10`, version `>0`; ACTIVE mewajibkan terminal fields/reason null; CONSUMED hanya `consumed_at` non-null; RELEASED hanya `released_at`+reason non-null.
- Partial index `loyalty_reservations_account_active_idx(account_id,order_id) WHERE status='ACTIVE'`; index `loyalty_reservations_order_status_idx(order_id,status)`.
- Row tidak dihapus. Hanya conditional transition `ACTIVE→CONSUMED|RELEASED`; terminal replay adalah no-op.

Tambahan `orders` selain kolom snapshot di bagian utama:
- `loyalty_account_id TEXT NULL REFERENCES loyalty_accounts(id) ON DELETE RESTRICT`.
- `redeemed_points BIGINT NOT NULL DEFAULT 0`.
- Constraint `orders_loyalty_snapshot_chk`: `redeemed_points BETWEEN 0 AND 180000000000`, `loyalty_discount_rupiah=redeemed_points*10`; ketiga field loyalty harus nol/null bersama atau account non-null dengan nilai positif.
- Index `orders_loyalty_account_idx(loyalty_account_id,created_at DESC,id DESC) WHERE loyalty_account_id IS NOT NULL`.

### Port dan kontrak API
Module lain hanya memakai:
```text
LoyaltyAccountPort.getBuyerOrganizerAccountForUpdate(buyerId,organizerId)
LoyaltyLedgerPort.appendUnique(entry)
LoyaltyReservationPort.reserveForOrder(...)
LoyaltyReservationPort.releaseActive(orderId,reason)
LoyaltyReservationPort.consumeActive(orderId)
LoyaltySettlementPort.settlePaidOrder(...)          // implementasi RFC-009
LoyaltySettlementPort.applyCompletedRefund(...)     // implementasi RFC-009
```

`GET /api/loyalty/accounts/{organizerProfileId}`
- Auth buyer ACTIVE; hanya akun actor sendiri; `private,no-store`; respons `200 {organizer:{id,name},balancePoints,debtPoints,reservedPoints,availablePoints,rate:{rupiahPerPoint:10,maxCheckoutPercent:20},cashValue:false,sandbox:true}`.
- Akun belum ada menghasilkan nilai nol tanpa membuat row. Cross-buyer lookup tidak tersedia.

`GET /api/loyalty/accounts/{organizerProfileId}/ledger?cursor&limit=1..50`
- Auth owner; keyset `occurred_at,id`; respons entry aman `{type,pointsDelta,orderNumber,occurredAt}` tanpa actor/provider/internal source key.

Endpoint summary/order memakai `redeemPoints` sebagaimana kontrak utama. Redemption `0|undefined` tidak membuat account/reservation. UI wajib menampilkan poin tersedia, cap 20%, diskon, total payable, “tidak dapat diuangkan”, dan organizer pemilik poin.

### Algoritma transaksi dan locking
```text
summarize(actor,event,items,requestedPoints):
  load current prices/eligibility
  subtotal = sum(unitPrice * quantity)
  organizer = event.organizerProfileId
  account = read actor+organizer projection
  validate requested <= floor(floor(subtotal*20/100)/10)
  validate requested <= availablePoints
  return snapshot preview; no reservation

createOrder(...):
  transaction SERIALIZABLE:
    claim idempotency; lock event
    if requestedPoints>0:
      account = upsert then SELECT FOR UPDATE by actor+event.organizer
      require organizer exact; recompute available and cap from locked prices
    lock ticket types ORDER BY id; validate inventory and price
    create order with subtotal, points, discount, totalPayable
    create inventory reservations and increment reserved inventory
    if points>0:
      guarded increment account.reserved_points where balance-reserved-debt>=points
      create ACTIVE loyalty reservation unique by order
    append audit; complete idempotency response

releaseOrder(orderId,reason):
  transaction:
    lock order; lock loyalty account if referenced; lock ticket types ORDER BY id
    release inventory once
    conditional ACTIVE→RELEASED loyalty reservation
    if transitioned: decrement reserved_points exactly once
    transition order; append one audit
```
- Semua flow expiry/cancel/failure mengikuti lock `order → loyalty account → ticket types`. Retry deadlock/serialization maksimum tiga. Tidak ada optimistic update.
- Idempotency request hash memasukkan `redeemPoints`; key sama dengan points berbeda adalah `IDEMPOTENCY_KEY_REUSED`.

### Keamanan, error, logging, dan monitoring
- Organizer diturunkan dari event database, bukan request. Buyer ID dari session. Tidak ada endpoint admin untuk memberi/mengubah poin manual pada MVP.
- Ledger trigger dan application role mencegah edit/delete; account projection hanya berubah dalam transaction yang juga menambah ledger atau mengubah reservation.
- Log/audit tidak memuat free-text, saldo lengkap, atau source key mentah; allowlist ID internal, points bucket, action, outcome, duration, correlation. Analytics hanya penggunaan agregat.
- Metrik reserve/release/consume, conflict, insufficient, debt, projection-vs-ledger reconciliation; alert pada `reserved>balance`, duplicate source, atau mismatch rekonsiliasi.

### Pengujian, rollout, acceptance, dan DoD
- `F75-UNIT-001`: rasio Rp10, floor cap 20%, subtotal kecil, zero points, BIGINT boundary, dan no float.
- `F75-INT-002`: akun unik buyer-organizer; poin organizer A ditolak pada B; ownership/API projection aman.
- `F75-CONC-003`: dua checkout atas poin tersisa yang sama hanya satu reserve; balance/reserved valid.
- `F75-TIME-004`: points tidak expiry; order tepat expiry melepas inventory+points sekali.
- `F75-IDEM-005`: create/replay/expiry/failure/cancel/event-cancel tidak menggandakan reservation, release, counter, atau audit.
- `F75-DB-006`: ledger update/delete ditolak; unique source dan constraints bekerja di PostgreSQL nyata.
- `F75-E2E-007`: summary → cap/error → confirm → countdown → expiry/cancel → points available kembali; copy sandbox/no-cash accessible.

Rollout: (1) additive enum/table/order columns default nol; (2) backfill order lama `subtotal=total lama`, discount/points nol, `total_payable=total lama`, lalu contract kolom lama; (3) deploy read account dan reconciliation check; (4) enable summary; (5) enable reservation untuk allowlist; (6) aktifkan global setelah concurrency test. Rollback menutup redemption baru tetapi mempertahankan schema/ledger dan tetap menjalankan release pada order yang sudah memakai poin.

Acceptance F75 RFC-008: buyer hanya dapat mereservasi poin miliknya dari organizer event yang sama; discount selalu `points*10` dan ≤20% subtotal; order menyimpan snapshot immutable; reservation dilepas tepat sekali pada semua terminal non-Paid; poin tidak expiry/tunai.
