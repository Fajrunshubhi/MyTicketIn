# RFC-008 — Order, Inventori, Reservasi, dan Expiry

## Metadata dan urutan
- Status: Diusulkan.
- Fitur yang dimiliki: **F16, F23, F24, F25, F26, F27, F28, F59**.
- Kompleksitas: **Sangat tinggi**.
- Prasyarat: **RFC-001, RFC-002, RFC-003, RFC-004, RFC-005, RFC-006, dan RFC-007 wajib selesai dan lulus**.
- Pendahulu langsung: **RFC-007 — Katalog dan Discovery**.
- Penerus langsung: **RFC-009 — Payment dan Refund Sandbox**.
- RFC-009 hanya boleh dimulai setelah Definition of Done RFC ini lulus.
- Implementasi wajib sekuensial; RFC ini tidak membuat payment, webhook, refund, tiket, QR, atau check-in.
## Sasaran dan keputusan
Pembeli terautentikasi dapat membuat satu order untuk satu event dengan snapshot harga server-side dan reservasi tepat 15 menit tanpa overselling. Counter inventori, order, item, reservasi, dan idempotency record dibuat atomik di PostgreSQL. Waktu database menjadi otoritas. Retry checkout efektif tepat sekali untuk key dan payload yang sama.
## Ruang lingkup
- Pemilihan beberapa tipe tiket dari satu event, masing-masing 1–5 unit.
- Batas kumulatif lima unit per akun, event, dan tipe untuk Paid plus reservasi aktif.
- Ringkasan checkout server-side dan konfirmasi eksplisit.
- Lifecycle order `PENDING`, `PAID`, `FAILED`, `EXPIRED`, `CANCELLED`, `REFUNDED`; RFC ini hanya menghasilkan `PENDING`, `EXPIRED`, dan pembatalan internal sebelum payment.
- Counter `reserved_quantity` dan `paid_quantity` sebagai sumber ketersediaan konsisten.
- Reservasi 15 menit, expiry idempoten, scheduler multi-worker, dan status order pembeli.
- Idempotency key checkout berscope pengguna selama 24 jam.
## Non-scope
- Membuat transaksi provider, instruksi payment, webhook, refund, atau mengubah order menjadi Paid (RFC-009).
- Menerbitkan tiket/QR (RFC-010) dan check-in (RFC-011).
- Cart lintas event, kursi, voucher, fee, pajak, waiting list, dynamic pricing, guest checkout.
- Mengubah harga/kuota authoring; RFC ini hanya membaca konfigurasi RFC-005/006.
- Memilih provider scheduler; decision gate harus ditutup, adapter pemicu tetap tipis.
## Gap kondisi setelah RFC-007
- Detail event hanya menampilkan sale eligibility; tidak ada stok aktual atau checkout.
- `event_ticket_types.quota` belum memiliki counter reserved/Paid.
- Belum ada order, item snapshot, reservasi, idempotency store, atau expiry worker.
- Cache katalog dapat stale dan tidak dapat menjadi dasar keputusan kuota.
## Invarian dan transisi
- `0 <= reserved_quantity`, `0 <= paid_quantity`, dan `reserved_quantity + paid_quantity <= quota`.
- Ketersediaan adalah `quota - reserved_quantity - paid_quantity`, dihitung dari row terkunci.
- Semua item dalam order wajib berasal dari satu event Published, belum dimulai, tidak dihentikan, dan berada pada window jual.
- `expires_at` selalu `created_at + INTERVAL '15 minutes'` berdasarkan `transaction_timestamp()`.
- Pada `now >= expires_at`, order tidak lagi dapat dibayar; tepat pada batas waktu dianggap kedaluwarsa.
- Reservasi aktif adalah `released_at IS NULL`; pelepasan mengurangi counter tepat sekali.
- Transisi RFC ini: `PENDING→EXPIRED` dan `PENDING→CANCELLED`; status terminal tidak dapat kembali.
- Protokol lintas RFC: lock order dahulu, lalu seluruh tipe tiket menurut `id ASC`; RFC-009 wajib mengikuti urutan ini.
- Key sama+payload sama mengembalikan order sama; key sama+payload berbeda selalu `409`.

## Diagram aliran data tekstual
1. Client mengirim tipe, jumlah, dan `Idempotency-Key`, tanpa harga.
2. Boundary memvalidasi session, CSRF, body, key, rate limit, lalu menghitung canonical request hash.
3. Transaction mengklaim idempotency record dan mengunci semua tipe tiket terurut.
4. Service memvalidasi event, window, batas akun, dan ketersediaan dari database.
5. Order, snapshot item, reservasi, dan kenaikan counter dibuat dalam transaction yang sama.
6. Audit atomik ditulis; commit menghasilkan order `PENDING` dan expiry tepat 15 menit.
7. Scheduler memilih order due dengan `FOR UPDATE SKIP LOCKED`, melepas setiap reservasi aktif, lalu menandai `EXPIRED`.
8. UI selalu membaca ulang status server; timeout client tidak mengubah state lokal secara optimistik.

## Kontrak API
Semua response privat `Cache-Control: private,no-store`; Zod, correlation ID, envelope error, dan server authorization wajib.
### `POST /api/checkout/summary`
- Auth: user ACTIVE; CSRF; rate 30/user/menit.
- Request: `{"eventId":"...","items":[{"ticketTypeId":"...","quantity":2}]}`; 1–10 tipe unik.
- Respons 200: `{event,items:[{ticketTypeId,name,quantity,unitPriceRupiah,lineTotalRupiah,availability}],totalRupiah,currency:"IDR",reservationMinutes:15}`.
- Tidak membuat data; hasil dapat berubah saat konfirmasi.
### `POST /api/orders`
- Auth: user ACTIVE; CSRF; rate 10/user/menit.
- Header wajib `Idempotency-Key`: 16–128 karakter ASCII opaque; server menyimpan SHA-256.
- Request sama dengan summary ditambah `confirmed:true`.
- Respons 201 pertama/200 replay: `{order:{id,orderNumber,status:"PENDING",items,totalRupiah,currency:"IDR",expiresAt,serverTime}}`.
- `409 IDEMPOTENCY_KEY_REUSED` jika canonical payload hash berbeda; processing lama mengembalikan `409 IDEMPOTENCY_IN_PROGRESS` + `Retry-After: 1`.
### `GET /api/orders/{id}`
- Auth owner atau ADMIN; owner hanya projection miliknya.
- Respons 200: `{order:{id,orderNumber,event,items,totalRupiah,currency,status,expiresAt,serverTime}}`.
- `404` generik untuk bukan owner; ADMIN access dicatat.
### `GET /api/orders?cursor&limit`
- Auth user ACTIVE; hanya order sendiri; limit 1–50 default 20.
- Respons 200 `{items:[...safeSummary],nextCursor}` dengan keyset `created_at,id`.
### `POST /api/internal/jobs/expire-orders`
- Auth: secret scheduler terpisah atau signed platform invocation; bukan session user.
- Request opsional `{"batchSize":100}`; maksimum 500.
- Respons 200 `{scanned,expired,releasedReservations,hasMore,durationMs}`.
- Invocation ID wajib untuk log; endpoint tidak mengembalikan data pembeli.
## State dan caching
- Database adalah source of truth order/inventori; tidak ada optimistic mutation.
- Countdown memakai `expiresAt-serverTime`, hanya informasional; server tetap memutuskan expiry.
- React state lokal hanya pilihan sebelum submit dan dialog konfirmasi.
- Detail publik boleh menampilkan kategori `AVAILABLE|LOW|SOLD_OUT`, tetapi endpoint checkout tidak pernah percaya cache.
- Setelah reserve/release, invalidasi tag `event:{id}` dan `events:list` best effort; kegagalan cache tidak rollback transaksi.
- Idempotency response disimpan tersanitasi; key mentah tidak disimpan atau dicatat.

## Algoritma/pseudocode
```text
createOrder(actor, key, input):
  canonical = sort unique items by ticketTypeId; requestHash = sha256(canonical)
  transaction SERIALIZABLE:
    claim actor/scope/sha256(key); replay or reject mismatch
    lock event; lock ticket types ORDER BY id
    dbNow = transaction_timestamp()
    validate Published, windows, same event, not stopped, before event
    for each type:
      existing = Paid + active reservation quantity for actor/event/type
      require existing + requested <= 5
      require quota - paid_quantity - reserved_quantity >= requested
    create order(createdAt=dbNow, expiresAt=dbNow+15m), items, reservations
    increment each reserved_quantity with guarded UPDATE
    append audit; complete idempotency response
  retry serialization/deadlock max 3 with jitter; return

expireBatch():
  transaction:
    select due PENDING orders where expires_at <= statement_timestamp()
      order by expires_at,id for update skip locked limit N
    for each order:
      lock ticket types by id
      for active reservations: decrement reserved_quantity; mark released EXPIRED
      conditional update order PENDING→EXPIRED; append one audit
```

- Detail event RFC-007 memperoleh selector jumlah dan CTA “Lanjutkan checkout” hanya saat eligible.
- Summary menampilkan snapshot nama, jumlah, harga Rupiah, total tanpa fee, dan peringatan harga/stok divalidasi ulang.
- Setelah order dibuat, fokus menuju heading status dan countdown `15:00`; saat nol, refresh status server.

## Error, log, dan monitoring
- Kode: `CHECKOUT_INVALID`, `EVENT_NOT_PURCHASABLE`, `SALE_NOT_ACTIVE`, `PURCHASE_LIMIT_EXCEEDED`, `INVENTORY_UNAVAILABLE`, `PRICE_CHANGED`, `ORDER_NOT_FOUND`, `ORDER_EXPIRED`, `IDEMPOTENCY_KEY_REQUIRED`, `IDEMPOTENCY_KEY_REUSED`, `IDEMPOTENCY_IN_PROGRESS`, `EXPIRY_JOB_UNAUTHORIZED`, `ORDER_CONFLICT`.
- Log: correlation ID, order ID, event ID, jumlah tipe/unit, outcome, conflict/retry, duration; tanpa nama, email, key mentah, atau detail payment.
- Audit: `order.created`, `order.expired`, `order.cancelled`; before/after allowlist dan actor SYSTEM untuk job.
- Analytics: `checkout_started`, `order_created`, `order_expired`; dedup berbasis order/action.
- Metrik: reserve success/reject, serialization retry, counter conflict, expiry lag p95/max, released quantity, job failure; alert invariant violation segera dan expiry lag >2 menit.
## Keamanan, performa, aksesibilitas, dan i18n
- Semua harga/status/ownership dihitung server; CSRF, rate limit, object authorization, dan parameterized SQL wajib.
- CUID tidak menggantikan authorization; response user lain tetap 404.
- 50 checkout bersamaan untuk satu tipe diuji 15 menit; overselling nol dan create order p95 target internal ≤2 detik.
- Lock terurut, batch `SKIP LOCKED`, projection eksplisit, tanpa `COUNT(*)` pada list.
- Form semantic, label jumlah, ringkasan error, focus management, status tidak hanya warna, target WCAG 2.1 AA.
- Layout 320 px tanpa overflow; Bahasa Indonesia, integer Rupiah, timestamp UTC ditampilkan pada timezone event.
## Dependensi dan fallback
- Memakai event/ticket type RFC-005/006, katalog RFC-007, auth RFC-002, audit/analytics RFC-003, dan fondasi RFC-001.
- Scheduler harus dipilih sebelum rollout; jika invocation eksternal gagal, operator dapat menjalankan command idempoten terautentikasi.
- Tidak ada expiry via timer browser. Jika cache gagal, baca database. Jika analytics gagal, transaksi tetap commit; audit/database gagal rollback.
- Jika provider scheduler belum dipilih, RFC tidak dapat dinyatakan selesai; tidak boleh membuat interval in-process pada runtime serverless.
## Kasus uji
- `F16-CONC-001`: 50 request pada sisa satu, tepat satu reservasi berhasil dan counter valid.
- `F23-INT-001`: tipe lintas event, jumlah nol/>5, window/stop-sale ditolak.
- `F23-INT-002`: batas kumulatif Paid+aktif per akun/event/type maksimal lima.
- `F24-INT-001`: harga dan total selalu dari database; perubahan sebelum confirm terdeteksi.
- `F25-INT-001`: snapshot, owner projection, order number, dan transisi invalid.
- `F26-TIME-001`: sebelum batas aktif; tepat `expires_at` expired; release sekali.
- `F27-CONC-001`: rollback request multi-item gagal tidak meninggalkan item/reservasi/counter parsial.
- `F28-INT-001`: same key/same payload replay; payload beda 409; timeout retry satu order.
- `F59-CONC-001`: dua worker dan replay job menghasilkan satu expiry/audit/release.
- `F59-RACE-002`: contract race expiry/payment memakai lock order dahulu dan boundary waktu konsisten.
- `F16-PERF-001`: 50 pembeli/5.000 kuota/15 menit, nol oversell dan latensi tercatat.
- E2E: detail→summary→confirm→countdown→expiry→stok kembali.
## Migrasi dan rollout
1. Pastikan regression RFC-001–007 lulus, decision gate scheduler ditutup, dan backup preview tersedia.
2. Tambah enum/tabel/counter default nol; validasi seluruh quota lama memenuhi constraint.
3. Deploy read availability, lalu summary, create order, dan status di balik feature flag.
4. Aktifkan scheduler pada preview, uji clock boundary, multi-worker, retry, dan expiry lag.
5. Load test konkurensi sebelum membuka checkout demo; monitor counter dan audit.
6. Rollback menutup checkout/scheduler; data order tidak dihapus, migration contract ditunda sampai aman.
## Risiko dan mitigasi
- Overselling/lost update: row lock terurut, guarded update, constraint, dan concurrent PostgreSQL test.
- Deadlock multi-item: sort ID dan retry terbatas.
- Clock client salah: waktu database + `serverTime`.
- Job terlambat: stok tetap dianggap aktif sampai transaksi release; alert expiry lag dan job manual idempoten.
- Key abuse/storage growth: hash, scope per actor, rate limit, expiry 24 jam, cleanup terjadwal.
- Cache stale: hanya label; checkout memvalidasi database.
- Race payment mendatang: protokol lock dan batas `now < expires_at` wajib RFC-009.
## Kriteria penerimaan per fitur
- **F16:** ketersediaan konsisten `quota-paid-reserved`, tidak negatif, dan checkout bersamaan tidak melampaui kuota.
- **F23:** pembeli memilih tipe satu event dan jumlah positif dengan batas kumulatif lima per akun/event/type.
- **F24:** ringkasan dan total dihitung ulang server, dikonfirmasi, serta perubahan ditampilkan jelas.
- **F25:** order unik menyimpan owner/snapshot/status dan hanya transisi serta akses yang sah diterima.
- **F26:** order dan reservasi dibuat atomik selama tepat 15 menit lalu dilepas sekali.
- **F27:** sisa satu hanya memberi satu keberhasilan dan kegagalan multi-item tidak parsial.
- **F28:** retry key+payload sama mengembalikan order sama; key reuse berbeda ditolak.
- **F59:** scheduler idempoten, multi-worker-safe, tidak meng-expire non-Pending, dapat dipantau dan diulang.
## Definition of Done
1. Seluruh prasyarat RFC-001–007 dan regression suite lulus sebelum implementasi/penutupan RFC ini.
2. Migration, constraints, indeks, Prisma mapping, backup, dan rollback diuji pada PostgreSQL preview.
3. Invarian kuota, tepat 15 menit, batas akun, idempotensi, dan lock order dibuktikan test deterministik.
4. Unit/integration/security/E2E/concurrency/performance F16/F23–F28/F59 lulus; module branch coverage ≥90%.
5. Scheduler terpilih, multi-worker-safe, expiry lag termonitor, dan prosedur recovery diuji.
6. UI mobile Indonesia, state recovery, no optimistic commerce, serta WCAG 2.1 AA terverifikasi.
7. Format/lint/typecheck/build/test/security scan lulus tanpa blocker, Critical/High, TODO, atau secret.
8. Tidak ada payment, provider SDK, webhook, refund, ticket, QR, check-in, atau forward implementation RFC-009+.
9. RFC-009 baru dimulai setelah exit criteria ini disetujui.
