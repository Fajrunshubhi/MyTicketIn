# RFC-016 — Production Payment dan Financial Ledger

## Metadata dan urutan

- Status: **Deferred**.
- Klasifikasi: roadmap komersial; bukan bagian MVP akademik.
- Referensi roadmap: **F63** dan **F73** tetap `Won't Have` pada MVP.
- Prasyarat wajib: **RFC-015 selesai dan lulus**, sehingga seluruh prasyarat transitif RFC-001–014, UAT akademik, dan Commercial Entry Gate juga telah terpenuhi.
- Pendahulu langsung: **RFC-015 — Legal, Privasi, dan KYC/KYB**.
- Penerus langsung: **RFC-017 — Settlement, Payout, dan Reconciliation**.
- Mode rollout wajib: **dark-mode**; credential dan endpoint live tidak aktif.
- Larangan mutlak: **tidak ada live charge sampai gate RFC-020 disetujui eksplisit**.
- RFC-017 tidak boleh dimulai sebelum Definition of Done RFC-016 lulus.

## Kedudukan

RFC ini merancang payment produksi dan ledger finansial, tetapi tidak mengotorisasi pemindahan uang.
Semua kontrak provider, fee, tax, merchant-of-record, accounting treatment, dan operational ownership menunggu keputusan bisnis/legal/finance.
Istilah akun ledger di dokumen ini adalah model teknis usulan, bukan pendapat akuntansi atau pajak.

## Sasaran

1. Memisahkan domain Order dari payment gateway produksi melalui port canonical.
2. Menetapkan keputusan merchant of record (MoR) sebagai gate, bukan asumsi.
3. Menyediakan payment intent, webhook inbox, lifecycle, refund/dispute reference, dan idempotensi produksi.
4. Menyediakan ledger double-entry append-only dengan posting seimbang dan reversal.
5. Menyediakan konfigurasi fee/tax yang versioned, efektif, dan dapat diaudit.
6. Mengisolasi credential sandbox, shadow, dan production secara fail-closed.
7. Memvalidasi seluruh alur dalam dark-mode tanpa mengirim live charge.

## Ruang lingkup

- Production-capable `PaymentGateway` port dan adapter candidate.
- Payment account/routing profile per environment dan legal entity.
- Payment intent, payment attempt, webhook event, provider status mapping, dan reconciliation reference.
- Double-entry ledger: journal, posting, account, balance projection, reversal, serta invariant debit=credit.
- Fee/tax rule configuration dan snapshot per order/payment.
- Credential isolation, key rotation, webhook signature, audit, observability, dan incident controls.
- Shadow/dark-mode evaluation dengan request tidak dikirim ke endpoint live.
- Fondasi payable yang akan digunakan RFC-017.

## Non-scope

- Live charge, capture, refund finansial nyata, atau penggunaan credential production.
- Settlement, payout organizer, beneficiary account, reserve/hold release, atau reconciliation settlement; dimiliki RFC-017.
- Menentukan MoR, tarif fee, perlakuan pajak, pihak pemungut, invoice, atau chart of accounts final.
- Chargeback/dispute operations penuh; hanya reference/event envelope bila diputuskan perlu untuk ledger.
- Mengubah checkout sandbox MVP atau prioritas F63/F73.
- Multi-currency, FX, split payment, subscription, lending, atau stored value.

## Unresolved decision gates

1. Pihak merchant of record dan konsekuensi kontrak, refund, dispute, pajak, serta customer support.
2. Legal entity yang menandatangani perjanjian gateway dan memiliki merchant account.
3. Gateway/aggregator produksi, metode pembayaran, acquiring model, settlement behavior, SLA, biaya, dan limit.
4. Apakah authorize/capture terpisah diperlukan atau hanya immediate charge.
5. Payment expiry, retry, duplicate payment, late success, partial payment, overpayment, dan underpayment policy.
6. Refund produksi: full/partial, source of funds, fee treatment, cutoff, dan approval.
7. Dispute/chargeback lifecycle, evidence owner, reserve impact, dan ledger treatment.
8. Chart of accounts, account ownership, normal balance, posting date, cutoff, dan period close.
9. Revenue recognition dan klasifikasi gross/net; harus disetujui finance/accounting.
10. Fee types, payer, inclusion/exclusion dalam harga, rounding, effective time, dan refund allocation.
11. Tax type, taxable base, rate, withholding, invoice/faktur responsibility, rounding, dan reporting.
12. Idempotency scope/retention provider serta retry/timeout per operasi.
13. PCI scope, SAQ/assessment yang relevan, tokenization, hosted checkout, dan larangan data kartu.
14. Credential owner, secrets manager, rotation interval, break-glass, dual control, dan emergency revocation.
15. RTO/RPO, payment availability target, queue lag, recovery objective, dan on-call escalation.
16. RFC-020 live-charge gate: approver, evidence, transaction limit, allowlist, kill switch, dan rollback.

Tidak satu pun nilai bisnis/legal/finance di atas boleh dibuat oleh implementer.

## Prinsip arsitektur

- Modular monolith dan PostgreSQL tetap source of truth internal.
- Provider adalah source untuk fakta eksternal; webhook terverifikasi masuk inbox durable sebelum diproses.
- Redirect/browser callback tidak pernah menetapkan `SUCCEEDED`.
- Ledger journal/posting bersifat immutable; koreksi memakai reversal dan journal baru.
- Setiap journal harus seimbang dalam satu currency dan transaction boundary.
- Payment state dan accounting state dipisahkan.
- Fee/tax rule di-version dan di-snapshot; perubahan tidak menulis ulang transaksi lama.
- Integer minor unit digunakan; untuk Rupiah `currency=IDR` dan scale mengikuti keputusan final.
- Semua command uang menerima idempotency key dan actor/context.
- Production adapter fail-closed serta tidak dapat dibangun aktif sebelum RFC-020 gate.

## Arsitektur komponen tekstual

```text
Buyer Checkout
  → Payment Application Service
  → PaymentGateway port → Sandbox/Shadow Adapter
  → Provider candidate (non-live only)

Provider Webhook
  → signature verifier → durable inbox → event processor
  → Payment state transition → Ledger Posting Service
  → Journal + balanced postings + outbox → PostgreSQL

Order/Payment/FeeTax snapshots
  → Payable projection boundary → RFC-017

Admin Finance Console
  → read models / exception queues / reversal command
  → capability + dual control + audit
```

## Aliran data tekstual

1. Server menghitung total order, fee, dan tax dari rule version yang telah disetujui.
2. `PaymentIntent` dibuat idempoten tanpa memanggil endpoint live dalam dark-mode.
3. Shadow adapter memvalidasi bentuk request dan menghasilkan synthetic external reference.
4. Webhook sandbox/synthetic diverifikasi, disimpan dengan external event ID unik, lalu di-ack.
5. Processor mengunci payment, memvalidasi transisi, dan menyimpan provider event outcome.
6. Pada sukses pertama yang valid, service membuat journal template yang telah disetujui.
7. Database memverifikasi total debit sama dengan total credit sebelum journal menjadi posted.
8. Koreksi menghasilkan reversing journal dan replacement; row posted tidak diubah/dihapus.
9. Balance projection dibangun ulang dari postings dan bukan authority tersendiri.
10. Outbox memberi sinyal payable kepada RFC-017 setelah kontrak penerus tersedia.

## State machine **PROPOSED**

```text
PaymentIntent: CREATED → REQUIRES_ACTION → PROCESSING → SUCCEEDED
                    └→ EXPIRED | CANCELLED
                    └→ FAILED (retry policy TBD)
PaymentAttempt: CREATED → SENT → ACKNOWLEDGED → SUCCEEDED | FAILED | UNKNOWN
JournalEntry: DRAFT → POSTED → REVERSED
DarkRun: CREATED → VALIDATED → MATCHED | MISMATCHED | FAILED
```

Transisi final dan mapping provider tetap **PROPOSED** sampai provider serta payment policy dipilih.

- `payment_attempts`: `id`, `payment_intent_id`, `attempt_no`, `status`, `request_hash`, `provider_request_ref`, `sent_at`, `acknowledged_at`, `failure_code`; unique `(payment_intent_id, attempt_no)`.
- `production_payment_webhook_events`: `id`, `provider_code`, `external_event_id`, `event_type`, `payload_hash`, `signature_key_version`, `received_at`, `processed_at`, `outcome`; unique `(provider_code, external_event_id)`.
- `fee_tax_rule_versions`: `id`, `kind`, `code`, `currency`, `calculation_method`, `rate_basis_points`, `fixed_amount_minor`, `rounding_mode`, `payer`, `decision_ref`, `effective_from`, `effective_to`, `status`; unique `(code, effective_from)`.
- `order_financial_snapshots`: `id`, `order_id`, `subtotal_minor`, `fee_minor`, `tax_minor`, `total_minor`, `currency`, `rule_snapshot_json`, `calculation_hash`, `created_at`; unique `order_id`.
- `ledger_accounts`: `id`, `legal_entity_id`, `code`, `name`, `type`, `currency`, `owner_scope`, `status`, timestamps; unique `(legal_entity_id, code, currency)`.
- `journal_entries`: `id`, `journal_no`, `source_type`, `source_id`, `status`, `currency`, `effective_at`, `description_code`, `reverses_journal_id`, `idempotency_key_hash`, `posted_at`, timestamps; unique `journal_no`, unique `(source_type, source_id, idempotency_key_hash)`.
- `ledger_postings`: `id`, `journal_entry_id`, `account_id`, `side`, `amount_minor`, `line_no`, `dimensions_json`, `created_at`; check `amount_minor > 0`; unique `(journal_entry_id, line_no)`.
- `ledger_balance_projections`: `account_id`, `as_of_sequence`, `debit_minor`, `credit_minor`, `balance_minor`, `rebuilt_at`; projection dapat direbuild, unique `account_id`.
- `payment_dark_runs`: `id`, `order_id`, `candidate_provider_code`, `request_hash`, `expected_amount_minor`, `simulated_response_hash`, `status`, `mismatch_codes`, `created_at`; tanpa credential/live request.

### Invariant database **PROPOSED**

1. `amount_minor > 0` untuk intent charge; zero-value flow diputuskan terpisah.
2. Satu order hanya memiliki satu successful production payment kecuali policy duplicate disetujui.
3. Journal `POSTED` memiliki minimal dua posting dan `SUM(DEBIT)=SUM(CREDIT)`.
4. Posting journal `POSTED` tidak dapat di-update/hard-delete oleh role aplikasi.
5. Reversal mereferensikan satu journal posted dan totalnya tepat berlawanan.
6. Currency seluruh posting sama dengan journal/account; multi-currency dilarang.
7. Snapshot fee/tax immutable setelah payment attempt dikirim.
8. Dark run tidak boleh menyimpan credential atau provider live response.

Pemeriksaan balance kemungkinan memerlukan deferred constraint/transaction service dan database trigger terbatas; mekanisme final harus dibuktikan pada migration review.

## Kontrak provider **PROPOSED**

```text
ProductionPaymentGateway.createPayment(input, idempotentContext) → GatewayPayment
ProductionPaymentGateway.getPayment(externalRef) → GatewayPaymentStatus
ProductionPaymentGateway.cancelPayment(externalRef, idempotentContext) → GatewayOperation
ProductionPaymentGateway.refundPayment(input, idempotentContext) → GatewayRefund
ProductionPaymentGateway.verifyWebhook(rawBody, headers) → VerifiedPaymentEvent
```

`refundPayment` ada untuk contract readiness, tetapi implementasi live tetap disabled sampai gate dan policy terkait disetujui.

## Kontrak API **PROPOSED**

- `POST /api/orders/:orderId/production-payment-intents` — owner, idempotent; disabled sampai RFC-020.
- `GET /api/orders/:orderId/production-payment` — owner, safe status, `private,no-store`.
- `POST /api/webhooks/production-payments/:provider` — sandbox/shadow, signature, inbox unik, 202.
- `GET /api/admin/finance/payments` — `FINANCE_READ`, cursor pagination, filter URL.
- `GET /api/admin/finance/payments/:id/ledger` — journal/posting aman tanpa payload provider.
- `POST /api/admin/finance/journals/:id/reverse` — `FINANCE_POST`, idempotent, maker-checker.
- `POST /api/internal/jobs/process-payment-events` — signed worker, retry, quarantine.
- `POST /api/internal/dark-runs/payments` — preview/shadow synthetic tanpa network live.

Error minimum: `COMMERCIAL_PAYMENT_DISABLED`, `LIVE_CHARGE_GATE_REQUIRED`, `PAYMENT_ALREADY_SUCCEEDED`, `PAYMENT_STATE_CONFLICT`, `PROVIDER_STATUS_UNKNOWN`, `WEBHOOK_SIGNATURE_INVALID`, `LEDGER_UNBALANCED`, `JOURNAL_IMMUTABLE`, `FEE_RULE_UNDECIDED`, `TAX_RULE_UNDECIDED`, dan `MERCHANT_OF_RECORD_UNDECIDED`.

## Fee dan tax configuration

- Rule selalu versioned, memiliki `decision_ref`, approver, effective interval, currency, payer, formula, dan rounding.
- Kalkulasi server-only, deterministic, dan menghasilkan breakdown serta calculation hash.
- Overlap effective interval untuk code yang sama ditolak.
- Rule draft tidak boleh dipakai transaksi; perubahan retroaktif dilarang.
- Nilai rate, nominal, dan tax classification **tidak ditentukan RFC ini**.
- Invoice/faktur/evidence output ditunda sampai owner dan kontrak diputuskan.

## Ledger posting policy **PROPOSED**

- Template posting diberi version dan decision reference.
- Source event yang sama menghasilkan journal yang sama secara idempoten.
- Journal disusun `DRAFT`, divalidasi balance/account/currency/period, lalu atomik menjadi `POSTED`.
- Closed period, backdating, manual journal, dan approval threshold tetap decision gate.
- Balance query menjumlah posting atau memakai projection yang dapat diverifikasi/rebuild.
- Tidak ada direct balance mutation dan tidak ada delete untuk transaksi finansial.

## State management dan caching

- PostgreSQL adalah source of truth PaymentIntent, journal, dan posting.
- Provider status hanya masuk melalui verified webhook atau server-side reconciliation query.
- UI payment memakai refetch/poll terbatas; tidak ada optimistic success.
- Finance filter/pagination berada di URL; form lokal tidak menyimpan nominal authority.
- Payment, fee/tax, ledger, dan balance response `private,no-store`.
- Projection/cache boleh mempercepat read, tetapi keputusan finansial memverifikasi posting sumber.

## Credential isolation dan keamanan

- Secret terpisah per environment, legal entity, provider, dan merchant account.
- Production secret tidak tersedia pada build/deploy dark-mode; network egress live provider diblokir.
- Env validator menolak kombinasi `LIVE_CHARGES_ENABLED=true` sebelum signed RFC-020 gate artifact.
- Key version dicatat, value tidak pernah dicatat; rotasi dan overlap verification didukung.
- Hosted payment/tokenization diprioritaskan; TicketIn dilarang menyimpan PAN, CVV, PIN, OTP, atau payment credential.
- Webhook memakai signature, raw body, replay window, event uniqueness, rate limit, dan payload size limit.
- Aksi reversal/config memakai step-up auth, least privilege, maker-checker, reason, dan audit.
- Finance export dienkripsi, expiry, akses terbatas, dan tidak memuat provider secret.

## Kepatuhan

- PCI scope dan kontrol final ditentukan assessment yang berwenang, bukan RFC.
- UU PDP, privacy notice, purpose, retention, dan DSR mengikuti RFC-015.
- MoR, tax, accounting, consumer terms, refund, dan dispute membutuhkan sign-off legal/finance.
- Provider agreement, DPA, subprocessor, data residency, sanctions/fraud obligations tetap gate.
- Audit evidence harus memenuhi policy retensi final; log teknis bukan buku besar.

## Error, logging, dan observability

- Timeout create menghasilkan `UNKNOWN/PROCESSING`, bukan retry charge otomatis tanpa lookup/idempotency.
- Status provider tak dikenal masuk exception queue dan alert; tidak dipetakan ke sukses.
- Duplicate/out-of-order webhook aman dan menyimpan outcome.
- Structured log memuat payment ID pseudonymous, event type, transition, amount bucket opsional yang disetujui, duration, outcome, correlation ID.
- Dilarang log nominal sensitif jika tidak diperlukan, checkout URL, token, authorization header, payload mentah, atau account reference.
- Metrik: intent/attempt outcome, webhook invalid/lag, unknown status, posting failure, unbalanced rejection, dark mismatch.
- Kill switch dan runbook menghentikan command baru tanpa menghapus inbox/reconciliation.

## Kinerja dan reliability

- Target **PROPOSED**: create intent internal p95 ≤ 1,5 detik di luar latensi hosted redirect; webhook durable ack p95 ≤ 1 detik.
- Ledger posting event p95 ≤ 2 detik pada profil komersial yang kelak disetujui.
- Posting dan inbox memakai transaction pendek, index selektif, batch, dan `SKIP LOCKED`.
- Retry memakai exponential backoff+jitter dan bounded attempts.
- Ledger rebuild/checksum serta restore drill memverifikasi balance.
- SLA, kapasitas, RTO/RPO produksi wajib diputuskan; target MVP tidak diwariskan otomatis.

## Strategi pengujian

- Unit/property: mapping, transisi, fee/tax, posting/reversal, debit=credit, dan deterministic hash.
- Integration: idempotent intent, concurrent webhook, immutable posting, unique source, rebuild.
- Contract: sandbox/fake untuk timeout, duplicate, out-of-order, dan unknown.
- Security/E2E: authorization, secret/replay/SSRF/PCI canary, checkout → webhook → journal.
- Recovery/negative: crash/replay/rotation/restore/kill switch; tidak ada live DNS, call, atau credential.

## Rollout dark-mode

1. Tetap `Deferred` sampai RFC-015 dan seluruh decision gate RFC-016 lulus.
2. Migration additive pada branch terisolasi; deploy fake/sandbox dengan payment disabled.
3. Jalankan synthetic calculation/dark runs tanpa network live dan verifikasi seluruh gate.
4. Production tetap read-only/dark; endpoint mengembalikan `LIVE_CHARGE_GATE_REQUIRED`.
5. Secret absent dan egress blocked; live charge hanya dipertimbangkan pada **RFC-020 gate**.
6. Rollback menghentikan worker/entry point tanpa menghapus atau menulis ulang journal.

## Kriteria penerimaan

1. Keputusan MoR/provider/payment/fee/tax/accounting/PCI/owner terdokumentasi.
2. Adapter sandbox/fake, status mapping, inbox, serta intent idempotency lulus.
3. Journal seimbang/immutable/reversible/rebuildable; fee/tax snapshot deterministic.
4. Credential isolation, rotation, deny-live, dan kill switch terbukti.
5. Dark run menemukan mismatch tanpa live charge.
6. Tidak ada Critical/High; audit bebas data terlarang.
7. F63/F73 tetap roadmap dan MoSCoW MVP tidak berubah.

## Risiko dan mitigasi

- Double charge/unbalanced ledger: idempotency, timeout lookup, atomic validator, database/property test.
- Salah fee/tax/status: approved version, deterministic snapshot, explicit mapping, unknown queue.
- Credential/environment leak: isolation, egress deny, canary, fail-fast.
- Asumsi MoR/accounting: hard gate dan sign-off legal/finance.
- Live tak sengaja: no production secret, route/network guard, negative test.
- Forward payout: hanya boundary event; RFC-017 tetap belum aktif.

## Definition of Ready

1. RFC-015 selesai dan seluruh decision gate material ditutup.
2. MoR/entity/provider/finance/tax/legal owners dan sign-off tersedia.
3. Threat model, PCI scope, credential plan, chart of accounts, dan templates disetujui.
4. API/schema **PROPOSED** final; sandbox, fixture, branch, dan budget tersedia.
5. Dark/live-deny/kill-switch/recovery plans disetujui.
6. Gate RFC-020 terdokumentasi tanpa diaktifkan.

## Definition of Done

1. Kriteria penerimaan, decision record, migration, module, console, dan runbook selesai.
2. Seluruh test lulus dengan evidence checksum/rebuild/restore/immutability/reversal.
3. Tidak ada blocker/critical atau Critical/High security/finance.
4. Deployment dark, secret absent, egress blocked, dan live charge mustahil.
5. Artifact bebas secret/data terlarang.
6. RFC-016 disetujui sebelum RFC-017; live charge tetap menunggu RFC-020.
