# RFC-009 — Payment dan Refund Sandbox

## Metadata dan urutan
- Status: Diusulkan.
- Fitur yang dimiliki: **F29, F30, F31, F32, F33**.
- Kompleksitas: **Sangat tinggi**.
- Prasyarat: **RFC-001, RFC-002, RFC-003, RFC-004, RFC-005, RFC-006, RFC-007, dan RFC-008 wajib selesai dan lulus**.
- Pendahulu langsung: **RFC-008 — Order, Inventori, Reservasi, dan Expiry**.
- Penerus langsung: **RFC-010 — E-ticket, QR, dan Wallet**.
- RFC-010 hanya boleh dimulai setelah Definition of Done RFC ini lulus.
- Hanya payment gateway sandbox; uang nyata, settlement, payout, fee, pajak, dispute, dan credential produksi dilarang.
- RFC ini tidak membuat Ticket, QR, wallet, scanner, atau check-in.
## Sasaran dan keputusan
Order Pending memperoleh transaksi payment sandbox melalui adapter provider yang dipilih pada decision gate. Hanya webhook dengan signature sah dan event ID unik dapat mengubah status. Pemrosesan efektif tepat sekali, termasuk replay. Callback sukses pada atau setelah `expires_at`, atau setelah order Expired, tidak menghidupkan reservasi dan masuk rekonsiliasi admin tanpa penerbitan tiket.
## Ruang lingkup
- Port `PaymentGateway` dan satu adapter provider sandbox terpilih plus fake deterministik untuk test.
- Pembuatan payment idempoten satu payment aktif per order dan instruksi metode sandbox.
- Metode QRIS, virtual account, dan e-wallet hanya jika akun sandbox mendukung.
- Verifikasi raw-body signature, timestamp/replay policy provider, event dedup, dan mapping status.
- Transisi payment/order serta konversi reservasi `reserved→paid` secara atomik.
- Rekonsiliasi callback sukses terlambat dan mismatch oleh admin dengan alasan/audit.
- Lifecycle refund sandbox dan pembatalan fulfillment melalui kontrak transaksi yang dilengkapi RFC-010.
## Non-scope
- Payment produksi, uang nyata, kartu, penyimpanan credential pelanggan, payout/settlement/ledger.
- Menandai Paid berdasarkan redirect, query client, atau polling provider tanpa verifikasi.
- Otomatis menerima callback terlambat, menghidupkan reservasi lama, atau oversell.
- Ticket issuance/QR (RFC-010), check-in (RFC-011), dashboard umum (RFC-012), notifikasi (RFC-013).
- Partial capture, chargeback, dispute, multi-provider routing, recurring payment.
## Gap kondisi setelah RFC-008
- Order/reservasi Pending tersedia, tetapi tidak ada transaksi provider atau status payment.
- Status `PAID` dan counter `paid_quantity` belum memiliki command.
- Belum ada raw webhook verification, external event dedup, rekonsiliasi, atau refund.
- Expiry worker memerlukan protokol race konkret dengan callback sukses.
## Aturan domain dan transisi
- Satu order memiliki maksimum satu payment; retry create mengembalikan payment yang sama.
- Nominal payment wajib sama persis `orders.total_rupiah`, currency `IDR`, environment `SANDBOX`.
- Status payment: `CREATED→PENDING|SUCCEEDED|FAILED|EXPIRED`; `PENDING→SUCCEEDED|FAILED|EXPIRED`; `SUCCEEDED→REFUNDED`.
- Order hanya `PENDING→PAID` jika webhook sukses sah, `dbNow < expires_at`, dan semua reservasi masih aktif.
- Sukses saat `dbNow >= expires_at` selalu kasus late, meski scheduler belum menandai order Expired.
- Pada sukses tepat waktu: lock order, lock tipe terurut, kurangi reserved, tambah paid, release `CONVERTED_TO_PAID`, lalu order Paid dan audit dalam satu transaction.
- Event webhook yang sama diproses sekali; event berbeda dengan state sama menjadi no-op auditable.
- Redirect hanya memberi pesan “menunggu konfirmasi”; database dari webhook adalah source of truth.
- Refund hanya order Paid, nominal `1..payment.amount_rupiah`, total refund Completed tidak boleh melebihi pembayaran.
- Refund biasa ditolak jika kelak terdapat Ticket Used; RFC-010 memasang `RefundFulfillmentGuard` tanpa mengubah kontrak ini.
## Diagram komponen tekstual
```text
Order Page → CreatePaymentService → PaymentGateway port → Sandbox Adapter
          └→ PaymentReadService → PostgreSQL
Provider Sandbox → POST webhook(raw bytes)
                 → SignatureVerifier → WebhookInbox
                 → ProcessPaymentWebhookService
                 → order/inventory/payment/audit transaction
Late/mismatch → ReconciliationQueue → Admin Resolve Service
Admin Refund UI → RefundService → PaymentGateway.refundSandbox
                              └→ RefundFulfillmentGuard (RFC-010 implementation)
```
## Diagram aliran data tekstual
1. Buyer meminta payment untuk order sendiri; service memvalidasi Pending dan belum expiry.
2. Row payment lokal `CREATED` diklaim sebelum call provider dengan idempotency reference stabil.
3. Adapter membuat transaksi sandbox; respons tersanitasi disimpan sebagai instruksi allowlist.
4. Provider mengirim raw webhook; signature diverifikasi sebelum JSON dipercaya.
5. Inbox menyimpan event ID unik, payload hash, hasil signature, dan body tersanitasi.
6. Event valid diproses dengan lock order pertama dan payment; replay mengembalikan 200 tanpa side effect.
7. Sukses tepat waktu mengonversi inventori dan Paid; sukses terlambat menyelesaikan expiry bila perlu lalu membuat reconciliation case.
8. Refund dibuat admin, dipanggil idempoten ke sandbox, lalu status final berasal webhook/status provider terverifikasi.

## Kontrak adapter provider
```text
PaymentGateway:
  createPayment({merchantReference,amountRupiah,method,expiresAt,idempotencyKey})
    -> {externalReference,status,instructions,providerExpiresAt}
  verifyWebhook({rawBody,headers,receivedAt})
    -> {valid,eventId,externalReference,eventType,amountRupiah,payloadHash,safePayload}
  refundSandbox({externalPaymentReference,refundReference,amountRupiah,reason})
    -> {externalRefundReference,status,payloadHash}
  getPaymentStatusSandbox(externalReference) -> mapped verified status
```
- Adapter hanya server-side, timeout 10 detik, retry maksimal dua untuk network/5xx dengan key sama.
- Mapping event provider ke enum exhaustive; event tidak dikenal ditolak/no-op tercatat, bukan diasumsikan sukses.
## Kontrak API
Semua endpoint user/admin `private,no-store`, Zod, correlation ID, error envelope, dan audit sesuai sensitivitas.
### `POST /api/orders/{orderId}/payment`
- Auth owner ACTIVE; CSRF; `Idempotency-Key` wajib; rate 5/order/menit.
- Request `{"method":"QRIS|VIRTUAL_ACCOUNT|EWALLET"}`.
- Respons 201/200 replay: `{payment:{id,status,method,amountRupiah,currency:"IDR",instructions,expiresAt,sandbox:true}}`.
- `instructions` allowlist per metode; tidak memuat secret/provider raw payload.
### `GET /api/orders/{orderId}/payment`
- Auth owner atau ADMIN; owner bukan miliknya menerima 404; respons 200 `{payment:{status,method,amountRupiah,instructions,providerExpiresAt,sandbox:true},orderStatus,serverTime}`.
### `POST /api/webhooks/payments/{provider}`
- Auth bukan session; signature provider atas raw body dan header wajib.
- Body maksimum 256 KB; content type allowlist; rate limit defensif tanpa memblokir retry sah.
- Respons 200 `{received:true}` untuk event valid pertama/replay; 401 signature invalid; 400 malformed; 202 untuk transient processing retry.
- Event ID sama+hash beda menjadi security alert dan `409 WEBHOOK_EVENT_COLLISION`.
### `GET /api/admin/payment-reconciliations`
- Auth ADMIN; cursor/limit/status; projection minim PII; respons 200 `{items:[{id,orderNumber,paymentId,reasonCode,providerReferenceMasked,createdAt,status}],nextCursor}`.
### `POST /api/admin/payment-reconciliations/{id}/resolve`
- Auth ADMIN; CSRF; `Idempotency-Key`; expectedVersion.
- Request `{"decision":"REJECT|ACCEPT_REFUND_SANDBOX","notes":"10..1000"}`.
- ACCEPT tidak pernah menerbitkan tiket/mengembalikan Paid; hanya memulai refund sandbox atau penyelesaian administratif.
### `POST /api/admin/refunds`
- Auth ADMIN; CSRF; request `{orderId,amountRupiah,reason}`; idempotency wajib; respons 201 `{refund:{id,refundNumber,status:"REQUESTED",amountRupiah,sandbox:true}}`.
### `POST /api/admin/refunds/{id}/decision`
- Auth ADMIN; CSRF; expectedVersion; request `{decision:"APPROVE|REJECT",reason}`.
- Approve menjalankan guard fulfillment lalu call provider; response status `PROCESSING|COMPLETED|FAILED`.
## State dan caching
- Order/payment/refund/reconciliation hanya dari database dan selalu `no-store`.
- Poll status UI minimum interval 3 detik, berhenti pada terminal, exponential backoff saat error, dan Page Visibility pause.
- Redirect provider tidak mengubah state; UI menunggu webhook dan menyediakan refresh manual.
- Tidak ada optimistic Paid/refund; provider instruction disimpan allowlist agar refresh tidak membuat payment baru.

## Algoritma/pseudocode
```text
processWebhook(raw, headers):
  verified = adapter.verifyWebhook(raw, headers) before parse trust
  persist/dedup inbox by provider+eventId and compare payloadHash
  if invalid: reject, audit webhook.rejected, return 401
  transaction:
    lock payment by external reference; lock order
    if inbox already PROCESSED: return replay 200
    validate reference, amount, currency, mapped transition
    dbNow = transaction_timestamp()
    if success and order=PENDING and dbNow < order.expires_at:
      lock ticket types ORDER BY id
      require all reservations active
      reserved -= qty; paid += qty; reservation release=CONVERTED_TO_PAID
      payment=SUCCEEDED; order=PAID; append audit; mark inbox PROCESSED
    else if success:
      if order=PENDING: expire and release using RFC-008 service
      payment=SUCCEEDED; create reconciliation LATE_SUCCESS/state mismatch
      mark inbox PROCESSED; do not issue fulfillment
    else apply trusted failure/expiry transition and release reservation once
```
## UI/UX
- Semua halaman dan metode diberi badge permanen “SANDBOX / TRANSAKSI UJI”.
- Instruksi per metode dapat disalin, memiliki expiry dan status live; data sensitif tidak ditampilkan.
- Redirect kembali menunjukkan “Konfirmasi sedang diproses”, bukan “berhasil”.
- Late callback menampilkan order tetap Expired dan informasi sedang direkonsiliasi tanpa janji tiket.
- Admin queue menampilkan reason, timeline, nominal, referensi tersamar, dan dialog keputusan beralasan.
## Error, log, keamanan, dan monitoring
- Kode: `PAYMENT_NOT_ALLOWED`, `PAYMENT_METHOD_UNAVAILABLE`, `PAYMENT_PROVIDER_UNAVAILABLE`, `PAYMENT_AMOUNT_MISMATCH`, `WEBHOOK_SIGNATURE_INVALID`, `WEBHOOK_MALFORMED`, `WEBHOOK_EVENT_COLLISION`, `PAYMENT_TRANSITION_INVALID`, `PAYMENT_LATE_SUCCESS`, `REFUND_NOT_ALLOWED`, `REFUND_AMOUNT_INVALID`, `REFUND_PROVIDER_FAILED`.
- Secret hanya env tervalidasi; sandbox hostname/account allowlist dan startup menolak credential/endpoint produksi.
- Signature dibanding timing-safe pada raw bytes; timestamp tolerance mengikuti provider; replay tetap dedup database.
- Log hanya provider, event/payment/order ID internal, hash prefix, mapping, outcome, latency, correlation; tanpa raw body, signature, VA lengkap, token, PII, atau secret.
- Metrik webhook valid/invalid/replay/late, processing p95, provider latency/error, reconciliation age, refund status; alert invalid spike, event collision, late case, atau webhook 5xx >1%.
- Webhook response p95 target ≤1 detik untuk penerimaan; transaksi proses target p95 ≤2 detik, pekerjaan retry boleh asynchronous terkontrol.
## Aksesibilitas dan i18n
- Status menggunakan teks+ikon, `aria-live` sopan, focus pada perubahan terminal, dan instruksi copy keyboard.
- Polling tidak menyebabkan focus jump; reduced motion dihormati.
- Bahasa Indonesia, Rupiah integer, waktu sesuai timezone event; label SANDBOX tidak hanya warna.
- Layout payment/admin queue berfungsi 320 px dan WCAG 2.1 AA.
## Dependensi dan fallback
- Wajib order/inventory RFC-008, auth RFC-002, audit/analytics RFC-003, event RFC-005–007.
- Provider sandbox wajib dipilih dan kemampuan signature/event ID/refund diverifikasi sebelum selesai.
- Fake deterministik hanya test. Jika provider down, status lokal tetap aman dan UI retry; tidak ada fake/no-op runtime produksi-demo.
- Jika refund API sandbox tidak tersedia, admin hanya dapat mencatat `REJECTED/FAILED` dengan alasan; F33 integrasi provider tetap Should Have dan batas ditampilkan.
- RFC-010 wajib mengimplementasikan `RefundFulfillmentGuard` untuk menolak Used dan membatalkan Unused secara atomik; sebelum ada tiket, guard membuktikan tidak ada fulfillment karena issuance belum tersedia.
## Kasus uji
- `F29-CONTRACT-001`: adapter create/retry nominal sama, metode terdukung, sandbox-only.
- `F30-E2E-001`: refresh/redirect tidak membuat payment atau Paid palsu.
- `F31-SEC-001`: signature salah/malformed/body besar ditolak tanpa mutasi.
- `F31-INT-002`: replay event sama dan event sukses berbeda tidak menggandakan counter/audit transisi.
- `F31-SEC-003`: event ID sama hash berbeda memicu collision alert.
- `F31-CONC-004`: webhook sukses vs expiry tepat batas; satu hasil deterministik, tanpa oversell.
- `F32-INT-001`: sukses setelah expiry membuat satu case, tidak menghidupkan reservation/order/tiket.
- `F32-E2E-002`: admin resolve beralasan, idempoten, auditable.
- `F33-INT-001`: transisi refund, amount aggregate, provider retry, Used guard contract.
- `F33-SEC-002`: non-admin, ownership bypass, credential/log leakage ditolak.
- Load/replay burst webhook tidak kehilangan event dan tidak membuat ticket (belum ada).
## Migrasi dan rollout
1. Regression RFC-001–008, backup preview, provider decision gate, endpoint callback publik, dan secret sandbox tervalidasi.
2. Tambah enum/tabel/index tanpa mengubah order; deploy adapter/fake test dan contract suite.
3. Aktifkan create/read payment di preview berlabel sandbox; webhook masih observe-only.
4. Replay corpus tersanitasi, lalu aktifkan processing untuk status gagal dan sukses dengan reconciliation.
5. Aktifkan refund/admin queue; lakukan E2E expiry race dan monitoring sebelum demo.
6. Rollback menonaktifkan create/webhook mutation/refund; inbox dipertahankan untuk replay setelah perbaikan, data finansial tidak dihapus.
## Risiko dan mitigasi
- Signature salah diterapkan: gunakan raw body, fixture provider, timing-safe compare, contract test.
- Webhook duplikat/out-of-order: unique inbox, state machine monotonic, row lock.
- Callback terlambat oversell: cutoff database ketat dan reconciliation-only.
- Provider timeout setelah create: merchant reference/idempotency stabil dan status lookup sandbox.
- Credential produksi tersisip: environment guard, hostname/account allowlist, secret scan.
- Refund dan tiket Used mendatang: fulfillment guard wajib sebelum RFC-010 selesai.
## Kriteria penerimaan per fitur
- **F29:** transaksi gateway hanya sandbox melalui adapter, nominal sama, metode terdukung, dan credential tidak bocor.
- **F30:** pembeli melihat instruksi/status konsisten; refresh tidak membuat payment baru; status tepercaya dari webhook.
- **F31:** signature invalid tanpa mutasi, replay efektif sekali, dan sukses tepat waktu mengubah Paid serta counter atomik.
- **F32:** sukses terlambat tidak menerbitkan tiket/menghidupkan stok dan muncul satu kali pada queue admin auditable.
- **F33:** lifecycle refund sandbox menyimpan nominal/alasan/admin/referensi, membatasi total, menolak Used melalui guard, dan tidak memindahkan uang nyata.
## Definition of Done
1. Seluruh RFC-001–008 dan regression suite lulus.
2. Provider sandbox, metode, signature, event ID, late behavior, dan kemampuan refund diputuskan serta didokumentasikan.
3. Migration/constraints/index, adapter contract, secret validation, backup, dan rollback diuji preview.
4. Webhook invalid/replay/out-of-order/late/race serta inventory conversion lulus di PostgreSQL nyata.
5. Unit/integration/security/E2E/performance F29–F33 lulus; module branch coverage ≥90%.
6. UI selalu berlabel sandbox, mobile, Indonesia, no optimistic payment, dan WCAG 2.1 AA.
7. Log/audit/metrics tersanitasi; alert webhook, reconciliation, dan provider diuji.
8. Format/lint/typecheck/build/test/security scan lulus tanpa blocker, Critical/High, TODO, atau credential produksi.
9. Tidak ada Ticket, QR, wallet, scanner, check-in, uang nyata, payout, atau forward implementation RFC-010+.
10. RFC-010 baru dimulai setelah exit criteria ini disetujui.
